# Architecture

## System context

LuckyDragon is a local desktop application with an optional browser-development mode. There is one renderer/UI, one in-memory state container, and one persistence adapter. No network application backend or remote database exists.

```text
User
  |
Electron BrowserWindow or development browser
  |
React Router -> pages -> reusable components
  |
AppContext -> transaction utilities / fund calculations
  |
storage adapter
  +-- Electron preload IPC -> main process -> JSON file
  +-- browser fallback -> localStorage
```

## Runtime boundaries

### Renderer

`src/main.tsx` mounts React and `BrowserRouter`. `src/App.tsx` defines login and protected routes. Pages compose reusable components; `AppContext` owns loaded application data, in-memory authentication status, and mutations.

The renderer has no direct Node access. In Electron it can call the two preload methods exposed on `window.electronAPI`.

### Preload bridge

`electron/preload.js` exposes:

- `loadData()` -> `data:load`
- `saveData(data)` -> `data:save`

Context isolation is enabled and Node integration is disabled. The save input currently has no runtime schema validation or size limits.

### Main process

`electron/main.js` creates the window, serves the Vite URL in development or `dist/index.html` in packaged mode, and reads/writes `money-manager-data.json` in Electron's `userData` directory.

Reads normalize missing top-level fields, but do not validate field types or nested records. Parse/read errors are swallowed and replaced with defaults. Writes replace the file synchronously and are not atomic. Renderer navigation and new-window behavior are not explicitly restricted.

## Frontend structure

| Module | Responsibility |
|---|---|
| `src/App.tsx` | Authentication-aware routing |
| `src/context/AppContext.tsx` | App state, login session, password and transaction mutations, persistence trigger |
| `src/store/storage.ts` | Electron/localStorage persistence abstraction |
| `src/types.ts` | Persisted/domain TypeScript interfaces |
| `src/utils/transactionUtils.ts` | Transaction normalization, classification, filtering, sums, labels, link notes |
| `src/utils/debtCalculations.ts` | Actual/planned summary calculations; name is broader than active usage |
| `src/pages/*` | Login, graph, actual transactions, planned transactions, password settings |
| `src/components/TransactionBoard.tsx` | Shared actual/planned list/filter/modal orchestration |
| `src/components/*Modal.tsx` | Add, detail, and fulfill dialogs |
| `src/components/FundOverview.tsx` | Summary cards and formula display |
| `src/index.css` | All application styling and responsive behavior |

## Route map

| Route | Access | Page |
|---|---|---|
| `/login` | Public; redirects if authenticated | Login |
| `/graph` | Protected | Summary and trend chart |
| `/transactions` | Protected | Actual received/paid records |
| `/planned` | Protected | Planned receivable/payable records |
| `/settings` | Protected | Change password |
| `/` or unknown protected path | Protected redirect | `/graph` |

Authentication is held only in React memory and is reset on reload/relaunch.

## Persisted data

```text
AppData
├── password: string
├── transactions: Transaction[]
│   ├── id, date, amount
│   ├── type: deposit | withdrawal
│   ├── status: actual | planned | processed
│   ├── counterparty, details
│   └── processedAt?, linkedActualId?, sourcePlannedId?, isAutoGenerated?
├── debts: Debt[]
└── debtPayments: DebtPayment[]
```

The file has no schema version. Backward compatibility currently consists of filling missing transaction `status`, `counterparty`, and `isAutoGenerated` fields and missing top-level arrays.

## Planned-to-actual lifecycle

```text
planned transaction
  --fulfill--> processed planned record + linked auto-generated actual record
  --reactivate from processed--> pending planned record; linked actual removed
```

Manual actual and pending planned records may be deleted after confirmation. Processed planned records and generated actual records are protected from direct deletion to preserve link integrity.

## Financial calculations

- Actual income = sum of actual deposits.
- Actual outcome = sum of actual withdrawals.
- Available funds / net profit = actual income minus actual outcome.
- Remaining = pending receivables minus pending payables.
- Net position = available funds plus remaining.
- “Total To Received/Total To Paid” currently combine pending amounts with actual received/paid amounts; terminology needs PM confirmation.
- Trend points aggregate actual income/expense per day and calculate per-day profit, not cumulative profit.

## External access

There are no business integrations. The only runtime web dependency is the Google Fonts stylesheet imported by `src/index.css`; it is optional because system fallbacks are declared. Removing the request by bundling a font or using system typography is included in security/offline hardening.

## Deployment and packaging

Vite produces `dist/`. electron-builder packages `dist/**/*` and `electron/**/*`, includes production dependencies, and targets Windows NSIS under `release/`. Existing output confirms the structure but is generated and ignored. No CI release workflow, update service, signing configuration, publishing configuration, or deployment environment exists.

## Architectural risks and intended direction

- Keep the local-first, no-backend design unless the PM explicitly changes scope.
- Add a versioned runtime schema before altering persisted data.
- Isolate persistence and domain mutations enough to test them without a rewrite.
- Validate all IPC input in the main process.
- Use atomic writes and recoverable backups for financial data.
- Decide the real security goal before choosing hashing, OS credential storage, or encryption.
- Split shared high-conflict files only when needed by assigned tasks; avoid speculative architecture work.
